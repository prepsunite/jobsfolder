### [Area 1] Issue #1: Grading Engine Fails to Disqualify Malpractice Attempts
- **File & Line Numbers:** `frontend/src/services/tpo.service.ts:L6310-L6315`
- **Severity:** P1 - Integrity Bypass
- **The Defect / Attack Vector:** The `calculateAttemptResult` function evaluates the `passed` boolean strictly based on whether the percentage exceeds `exam.passing_percentage`. Although it correctly calculates `isMalpractice` (e.g., from excessive tab switches), it fails to apply this to the `passed` variable. Consequently, a cheating candidate will still be marked as "passed" in the system if their score meets the threshold.
- **Current Deficient Code:**
  ```typescript
    const percentage = finalMaxScore > 0 ? Math.round((totalScore / finalMaxScore) * 1000) / 10 : 0;
    const passed = percentage >= (exam.passing_percentage || 40);

    const maxAllowedSwitches = exam.max_tab_switches_allowed ?? 3;
    const isMalpractice = statusOverride === 'TERMINATED_MALPRACTICE' ||
      (exam.enable_tab_switch_detection && tabSwitchCount >= maxAllowedSwitches);
  ```
- **The Better Way To Do It:** Ensure that any malpractice designation immediately overrides the passing logic, forcing a fail.
  ```typescript
    const percentage = finalMaxScore > 0 ? Math.round((totalScore / finalMaxScore) * 1000) / 10 : 0;

    const maxAllowedSwitches = exam.max_tab_switches_allowed ?? 3;
    const isMalpractice = statusOverride === 'TERMINATED_MALPRACTICE' ||
      (exam.enable_tab_switch_detection && tabSwitchCount >= maxAllowedSwitches);

    // Force fail on malpractice
    const passed = isMalpractice ? false : percentage >= (exam.passing_percentage || 40);
  ```

### [Area 1] Issue #2: Hidden Test Case Inputs/Outputs Leaking to Client
- **File & Line Numbers:** `frontend/src/services/codeExecution.service.ts:L510-L530`
- **Severity:** P1 - Integrity Bypass
- **The Defect / Attack Vector:** The `processExecResult` maps the execution results directly into the `EvaluatedTestCase` object, returning verbatim `input` and `expected_output` strings for every test case. A malicious user can intercept the React state or API response to view the internal criteria of hidden test cases designed to evaluate unhandled edge-cases.
- **Current Deficient Code:**
  ```typescript
    const processExecResult = (
      tc: TestCaseInput,
      execResult: ExecutionResult
    ): EvaluatedTestCase => {
      const stdin = tc.input || '';
      const expected = normalizeOutput(tc.expected_output || tc.output || '');

      if (execResult.isCompileError) {
        // ...
        return {
          input: stdin,
          expected,
          actual: err,
  ```
- **The Better Way To Do It:** Mask inputs and expected outputs if `tc.is_hidden` is true to protect evaluation integrity.
  ```typescript
    const processExecResult = (
      tc: TestCaseInput,
      execResult: ExecutionResult
    ): EvaluatedTestCase => {
      const isHidden = tc.is_hidden || false;
      const stdin = isHidden ? 'Hidden Test Case Input' : (tc.input || '');
      const expected = isHidden ? 'Hidden Expected Output' : normalizeOutput(tc.expected_output || tc.output || '');

      if (execResult.isCompileError) {
        // ...
        return {
          input: stdin,
          expected,
          actual: isHidden ? 'Hidden Actual Output' : err,
  ```

### [Area 3] Issue #3: Critical XSS Vulnerability in Experience Post Rendering
- **File & Line Numbers:** `frontend/src/components/ContentRenderer.tsx:L196-L200`
- **Severity:** P0 - Critical Security
- **The Defect / Attack Vector:** The `ContentRenderer` component blindly passes HTML generated by `marked.parse(preprocessed)` straight into `dangerouslySetInnerHTML`. Because unauthenticated users can submit crowd-sourced experiences via `SubmitExperiencePage.tsx`, an attacker can submit malicious Markdown (e.g., `<script>alert('XSS')</script>` or `<img src="x" onerror="stealTokens()">`), taking over admin or candidate sessions when they view the experience.
- **Current Deficient Code:**
  ```typescript
  return (
    <div
      className={wrapCls}
      dangerouslySetInnerHTML={{ __html: renderContentToHTML(content) }}
    />
  );
  ```
- **The Better Way To Do It:** Always utilize `DOMPurify` to aggressively sanitize HTML strings before inserting them into the DOM.
  ```typescript
  import DOMPurify from 'dompurify';

  // ...

  return (
    <div
      className={wrapCls}
      dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(renderContentToHTML(content)) }}
    />
  );
  ```

### [Area 3] Issue #4: Hidden Exams Leaking in Client-Side Filtering
- **File & Line Numbers:** `frontend/src/services/exam.service.ts:L214-L265`
- **Severity:** P2 - Logic Bug
- **The Defect / Attack Vector:** The `getAllExams` fetches all exams from the `exams` table unconditionally via `supabase.from('exams').select(...)` and then applies `filter(e => !e.isHidden)` strictly in JavaScript. Students observing their network traffic in DevTools can easily view the entire JSON payload of explicitly hidden/draft exams that they are not supposed to see yet.
- **Current Deficient Code:**
  ```typescript
      const { data: examsData, error: examsErr } = await supabase
        .from('exams')
        .select('id, company_slug, company_id, name, badge, content, old_papers, price, paper_tabs, is_public_exam, upvotes, google_doc_embed_url, google_doc_edit_url, is_deleted, companies(id, slug, name, logo_url, industry, about_company, description, is_deleted)')
        .eq('is_deleted', false)
        .order('name', { ascending: true });

      // ... Later down the line ...
      return includeHidden ? allMapped : allMapped.filter(e => !e.isCompanyHidden && !e.isHidden);
  ```
- **The Better Way To Do It:** Offload security filtering to the database level (Supabase RPC or exact `not.ilike` filtering) so the data never leaves the server.
  ```typescript
      let query = supabase
        .from('exams')
        .select('id, company_slug, company_id, name, badge, content, old_papers, price, paper_tabs, is_public_exam, upvotes, google_doc_embed_url, google_doc_edit_url, is_deleted, companies(id, slug, name, logo_url, industry, about_company, description, is_deleted)')
        .eq('is_deleted', false);

      // Filter out items with the HIDDEN_MARKER directly in the PostgreSQL query
      if (!includeHidden) {
          query = query.not('content', 'ilike', '%<!-- prepunite_hidden:true -->%')
                       .not('badge', 'ilike', '%<!-- prepunite_hidden:true -->%');
      }

      const { data: examsData, error: examsErr } = await query.order('name', { ascending: true });
  ```

### [Area 4] Issue #5: DPDP Act Violation - Orphaned PII in Attempt Records
- **File & Line Numbers:** `database/dpdp_retention_policy.sql:L60-L90`
- **Severity:** P1 - DPDP Privacy / Compliance
- **The Defect / Attack Vector:** The Postgres stored procedure `dpdp_delete_user_data(target_email)` implements the right to erasure by scrubbing `profiles`, `experiences`, `transactions`, `user_subscriptions`, and `user_paper_purchases`. However, it neglects the `student_exam_attempts` table, meaning the user's `user_email` and test responses are retained forever. This breaches the DPDP 2023 data retention rules.
- **Current Deficient Code:**
  ```sql
  UPDATE public.user_paper_purchases
  SET user_email = 'deleted_' || target_user_id || '@deleted.invalid'
  WHERE user_email = LOWER(target_email);

  -- Log the deletion in audit logs
  ```
- **The Better Way To Do It:** Ensure that the anonymization cascade fully encompasses the `student_exam_attempts` table.
  ```sql
  UPDATE public.user_paper_purchases
  SET user_email = 'deleted_' || target_user_id || '@deleted.invalid'
  WHERE user_email = LOWER(target_email);

  -- Ensure exam attempts are also anonymized to comply with DPDP
  UPDATE public.student_exam_attempts
  SET user_email = 'deleted_' || target_user_id || '@deleted.invalid'
  WHERE LOWER(user_email) = LOWER(target_email);

  -- Log the deletion in audit logs
  ```
